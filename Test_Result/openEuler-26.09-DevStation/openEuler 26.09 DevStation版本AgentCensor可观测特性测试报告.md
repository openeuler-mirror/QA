# 1     特性概述

AgentCensor是面向AI Agent的可观测与治理系统，其中CensorScope为被动式主机可观测模块。在不修改被观测程序、不要求Agent或工具接入SDK、不使用preload与主动上报协议的前提下，CensorScope通过procfs、eBPF tracepoint与运行时动态uprobe采集进程、文件、网络、IPC、stdio与应用负载观测，并把观测投影为可查询事件、负载分段与语义动作，落库SQLite供只读消费。

AI Agent的一次任务通常跨越主进程、会话worker、工具子进程、文件系统、网络与LLM服务。仅依赖Agent自身日志或工具返回值，只能看到“Agent声称做了什么”，无法回答工具实际启动了哪些进程、访问了哪些文件与网络、LLM交互内容是什么，以及这些行为属于哪一次工具调用。CensorScope将这些分散的低层事实关联到同一trace、session与call，形成可还原Agent行为过程的证据链。

本次测试重点验证以下特性：

* 旁路观测能力：通过`track-add`将已运行的根进程及其进程树纳入观测范围，不改变目标程序启动方式；
* 采集等级（`--level`）：L1/L2/L3三级能力集合，等级为本次运行属性，不写入配置文件；
* 非侵入进程树观测：识别根进程、子进程与后代进程，记录父子关系、执行信息、生命周期与进程身份变化；
* 非侵入工具调用采集观测：采集工具调用产生的进程、文件、网络、IPC与stdio行为，并准确归因到会话与工具调用；
* 非侵入LLM采集：通过运行时uprobe捕获TLS明文，形成HTTP、SSE、LLM、MCP等富语义观测结果；
* Agent动作记录导出：支持按trace、session、call过滤，提供lite/full与离线导出，以及只读SQL视图；
* 采集链路可靠性：引入运行期磁盘spool缓冲层，解耦ring buffer读取与解码、语义处理、数据库写入，降低高负载与存储背压下的数据丢失率；
* DSH集成：`censorscope-host`、`censorscope-ui`、`agentcensor-session-proxy`三个插件一行命令安装。

采集等级对应的采集内容如下：

| 等级          | 采集内容                                                      |
| ----------- | --------------------------------------------------------- |
| `L1`（默认）    | 进程基础（fork/exec/exit/signal + argv/executable）与文件基本操作（open/close/dup/read/write/路径） |
| `L2`        | L1 + mmap、网络端点、TLS明文负载                                    |
| `L3`        | 全量：L2 + IPC（pipe/socketpair，作为审计事件输出）与命令stdout/stderr正文    |

# 3     测试结论概述

## 3.1   测试整体结论

本次测试共执行73个测试用例，其中72个用例通过，1个用例未通过，发现一个问题单，对应AgentCensor Issue #1。该问题已完成修复，并完成回归验证。

测试范围共七类：单元测试、组件测试、特权采集测试、接口测试、集成测试、端到端测试，以及性能与容量测试。前六类对应模板的功能测试，共69个用例，采用”契约向下、证据向上”的分层方法，重点验证daemon生命周期与配置处理、L1/L2/L3采集等级边界、控制面接口、进程树与主机事件采集、存储与一致性、会话与工具调用归因、语义动作投影、导出与只读数据面以及DSH插件与UI闭环；性能与容量测试对应模板的DFX性能测试，共4个用例，覆盖控制面时延、采集吞吐与丢失、daemon内存预算、spool增长与回收、导出耗时与内存。

本次测试未包含兼容性测试、可靠性/韧性专项、安全专项与资料专项，相应结论章节标注为不涉及。

其中采集链路可靠性是本次测试关注的重点。优化前ring buffer读取、事件解码、进程信息补充、语义处理与SQLite写入位于同一条执行路径，数据库写入速度下降会直接拉长ring buffer的积压时间，在动态uprobe产生TLS明文事件形成突发流量时出现明显数据丢失。测试过程中形成Issue #1，通过引入持久化spool缓冲层完成修复：独立的collector actor独占eBPF collector与ring buffer，只负责处理高优先级控制命令、轮询ring buffer并把原始事件批次快速追加到append-only spool；后续consumer再从spool读取有界批次完成解码、归一化、语义处理与数据库写入。

整体测试结果表明，AgentCensor可观测特性的旁路采集、进程树还原、会话与工具调用归因、语义动作投影、导出与只读数据面功能运行正常；采集与后续消费实现解耦，数据库变慢造成的积压落在磁盘而非持续占用内存，采集缺口可由丢失账本按阶段计量。遗留问题已完成修复，当前无已知遗留风险，整体特性质量良好。

## 3.2   约束说明

* 本次测试基于openEuler 26.09 DevStation环境开展。
* eBPF采集依赖root权限、`/sys/kernel/btf/vmlinux`与可写`/sys/kernel/tracing`。上述条件不满足时daemon不退出，自动降级为`track-add`时的procfs进程树快照，此时不承诺持续的fork/exec/exit、文件与TLS事件。
* TLS明文采集为运行时动态uprobe能力，依赖目标进程实际加载的TLS库与可解析符号。静态链接、符号裁剪或非支持运行库场景下明文采集不可用，该情况由覆盖率诊断显式报告。
* spool为daemon运行期的磁盘缓冲层，不提供跨重启恢复能力。daemon重启后不依靠旧spool恢复未完成的语义处理，直接清理之前的spool文件。
* spool追加本身存在I/O成本。追加速度低于事件产生速度、spool达到容量上限或磁盘不可写时仍会产生采集缺口，该缺口由丢失账本按阶段计量，不作为完整结果输出。
* 采集等级由`--level`决定，是本次运行属性，不写入配置文件；`init`/`stop`/`status`不接受`--level`。
* daemon独占SQLite写入，其它程序通过文档化的只读视图或`censorscopectl export`读取数据。
* 性能测试数据受硬件、事件速率、负载体量及缓存状态影响，当前数据作为版本基线，用于后续版本按相同数据集比较。
* 会话与工具调用的精确归因需要被观测进程环境携带`CENSORSCOPE_SESSION_ID`（或配置的兜底env）与`DSH_CENSORSCOPE_CALL_ID`，由DSH插件注入。无环境变量的事件按调用span时间窗做唯一回补，不确定时保持未归因。

采集吞吐与数据丢失率（Issue #1）：

TC-NF-002（高吞吐背压与内存预算）为本次唯一未通过的用例，对应Issue #1。优化前ring buffer读取与解码、进程信息补充、语义处理、SQLite写入位于同一条同步路径，等价于让数据库的瞬时性能决定内核事件能否被及时取走；动态uprobe产生的TLS明文事件体量更大、频率更高，在突发流量下出现严重数据丢失。中间方案引入内存队列与独立writer线程后，数据库侧积压被转移到内存队列，队列设上限则达到上限后仍会整批丢弃事件、造成某个时间段完全没有数据，不设上限则在数据库持续变慢时带来RSS持续增长与OOM风险。

最终修复方案为引入持久化spool缓冲层，数据链路由`ring buffer → 单线程读取/解码/语义处理/写SQLite`演进为`ring buffer → collector actor → 运行期磁盘spool → 有界consumer → writer → SQLite`。collector actor独占eBPF collector与ring buffer，控制命令在actor内具有高于普通数据处理的优先级，旧数据只进入spool而不进入`track-add`的绑定等待队列，因此积压不会阻止新的观测绑定。

回归验证结论：ring buffer读取不再等待解码、语义处理与SQLite写入，突发TLS明文流量下ring buffer溢出造成的丢失显著下降；数据库变慢时backlog落在磁盘而非随延迟无限增长到进程内存，RSS达到稳定平台且不超过批准预算；数据库暂时失败时同一daemon运行期内可在故障解除后继续消费，spool水位可消化并回收安全segment；超载时kernel ring buffer、uprobe attach/read、spool append、spool capacity、解析、数据库与payload截断各阶段的损失分别进入丢失账本，计数独立且与注入量趋势一致。需要说明的是该方案不代表绝对零丢失：spool追加速度不足、spool满、磁盘不可写、daemon崩溃、uprobe附着失败或用户态内存读取失败时仍可能产生采集缺口，系统对这些情况均显式报告。

## 5.2   后续测试建议

1. 补充百万级event量级的导出测试，验证流式序列化路径与导出体量上限，避免大体量导出的峰值内存随输出体量成倍放大。
2. 补充兼容性测试设计与执行，覆盖aarch64架构、跨LTS SPx版本、升降级以及不同内核与OpenSSL版本组合，形成跨架构与跨版本基线。
3. 补充可靠性/韧性专项设计，增加fuzz与7*24长稳测试，观察spool水位、增长速度、回收速度、数据库消费延迟与RSS的长期趋势。
4. 补充安全专项设计，将当前分散在功能用例中的权限、隔离与负载内容保护断言归并为独立的安全测试项。
5. 补充资料测试项，在特性对外资料就绪后核对资料与实际行为的一致性，并附资料PR链接。
6. 补充更多TLS运行库与版本的uprobe符号解析测试，并针对静态链接、符号裁剪场景验证覆盖率诊断的准确性。
7. 针对采集进度与已落盘数据之间的进度差补充可观测指标。用户长时间高强度使用Agent时，真实eBPF进度与落库进度的差距会持续变大，可能导致最新若干轮工具调用的系统调用暂时不可见，建议在界面或诊断中显式呈现消费延迟。
8. 增加存储故障注入的覆盖范围，包括磁盘逐步耗尽、I/O延迟抖动与写权限动态回收等场景。
9. 补充容器与PID namespace场景下的身份隔离测试，覆盖容器内daemon与宿主ctl的部署组合。
